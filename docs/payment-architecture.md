# Payment Architecture & Razorpay Integration Manual — SkillSense

## Architecture Overview

Payment handling follows a modular provider abstraction pattern:

```text
                                  Payment UI (/pricing)
                                           │
                                  createOrder(plan_id)
                                           │
                                    PaymentService
                                           │
                                ┌──────────┴──────────┐
                                │ BasePaymentProvider │
                                └──────────┬──────────┘
                                           │
                                   RazorpayProvider
                                           │
                                ┌──────────┴──────────┐
                                │ Razorpay REST / SDK │
                                └─────────────────────┘
```

The application logic (credit wallets, assessment unlocks, user dashboards) does NOT directly call Razorpay APIs. Everything passes through `PaymentService` and `BasePaymentProvider`.

---

## 1. Provider Abstraction (`services/payment_service.py`)

`BasePaymentProvider` defines two mandatory contracts:
- `create_order(amount_in_subunits, currency, receipt, notes)`: Returns order details (`order_id`, `amount`, `currency`, `key_id`).
- `verify_signature(params)`: Validates HMAC-SHA256 signature generated by payment gateway.

`RazorpayProvider` implements `BasePaymentProvider` using the official `razorpay` SDK with a fallback HMAC signature engine.

---

## 2. Server-Side Payment Flow

```text
User selects plan on /pricing
           ↓
POST /api/payments/create-order { plan_id: "plan_single" }
           ↓
Backend validates active plan price (₹19) & creates Razorpay order
           ↓
Backend records payment entry in DB with status = 'CREATED'
           ↓
Frontend receives order ID & opens Razorpay Checkout JS modal
           ↓
User completes payment on Razorpay modal
           ↓
Razorpay returns razorpay_order_id, razorpay_payment_id, razorpay_signature
           ↓
POST /api/payments/verify { order_id, payment_id, signature }
           ↓
Backend verifies signature using HMAC-SHA256(order_id + "|" + payment_id, secret)
           ↓
Backend performs IDEMPOTENCY check:
  - If payment status is already 'SUCCESS' → return clean response without double crediting.
           ↓
Backend marks payment as 'SUCCESS' in database
           ↓
Backend atomically adds credits to user wallet via WalletService
           ↓
Backend logs immutable transaction in credit_transactions ledger
```

---

## 3. Security Principles Enforced

1. **Server-Side Price Source of Truth**:
   - The frontend never passes prices or credit amounts to order creation APIs. It only passes `plan_id`. The server fetches the price directly from `pricing_plans` table.

2. **Idempotent Credit Granting**:
   - Webhook or client verification calls cannot cause double-credit grants. Before granting credits, `PaymentService` verifies if the `payments` record status is already `SUCCESS`.

3. **HMAC-SHA256 Signature Verification**:
   - Razorpay secret `RAZORPAY_KEY_SECRET` is kept strictly server-side in `.env` and is never transmitted to client browsers.

---

## 4. Environment Variables Configuration

In `.env`:

```env
# Razorpay Credentials (TEST MODE)
RAZORPAY_KEY_ID=rzp_test_your_key_id_here
RAZORPAY_KEY_SECRET=your_razorpay_key_secret_here
```

To switch to production mode on Hostinger VPS, simply update `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` in `.env` and restart the Waitress / Docker container. Zero code edits required!
